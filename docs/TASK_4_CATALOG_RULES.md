# Задача 4. Общий Telegram-слой, Catalog и правила ввода

## Статус

**В процессе разработки.**

## Цель

Реализовать общие Telegram-компоненты и промежуточный слой между обработчиками и
Repository. Главное меню и бизнес используют единые функции отправки, клавиатуры,
FSM-формы и middleware из `bot/common.py`, вызывают методы `Catalog`, а пользовательские
значения проходят общие проверки с безопасными сообщениями об ошибках.

## Основные файлы задачи

```text
src/notebook_bot/bot/common.py
src/notebook_bot/logic/catalog.py
src/notebook_bot/logic/rules.py
```

Задача использует модели и JSON-хранилище задачи 2, но не читает файл напрямую. Она не
изменяет тексты, клавиатуры и callback из задачи 1.

## Общий Telegram-слой

`bot/common.py` должен предоставлять повторно используемые компоненты, которые нужны
`menu.py` и `business.py`:

- `ContextMiddleware`, получающий пользователя через `Catalog.user()` и передающий
  обработчикам `app` и `actor`;
- общие callback-константы и клавиатуры «Назад», «Отмена» и перехода в главное меню;
- функции отправки или редактирования Telegram-сообщений;
- общий `forms_router` и состояния последовательного ввода;
- преобразование ожидаемого `RuleError` в понятное сообщение пользователю.

В этом файле не размещаются правила владения бизнесом и операции JSON-хранилища. Он
обрабатывает Telegram update и передаёт данные сервисному слою.

## Методы Catalog

Минимальный сервисный контракт:

```text
user(...)
get_main_menu_data(...)
owner(...)
owned_business(...)
create_business(...)
business(...)
update_business(...)
services(...)
favorites(...)
favorite(...)
```

`owned_business()` сохраняет совместимость с текущим обработчиком `business.py`, а
внутреннюю проверку владельца выполняет через общий `owner()`.

## Правила

- один Telegram-пользователь создаётся один раз и обновляет отображаемое имя;
- у одного владельца может быть не более двух бизнесов;
- присланный callback не подтверждает право владельца;
- публичный просмотр не возвращает скрытые услуги;
- владелец может видеть свои скрытые услуги;
- избранное переключается без дубликатов;
- данные читаются и изменяются только внутри транзакции Repository;
- текстовые и числовые настройки проверяются до сохранения.

## Общие преобразования ввода

`rules.py` предоставляет:

```text
RuleError
text(...)
number(...)
minute(...)
hhmm(...)
intervals(...)
local_date(...)
```

`RuleError` содержит сообщение, которое разрешено показать пользователю. Ошибки Python,
содержимое JSON и внутренние идентификаторы хранилища пользователю не раскрываются.

## Границы задачи

В задачу не входят:

- расчёт свободных слотов;
- создание, перенос и отмена записи;
- календарь месяца;
- фоновые уведомления;
- SQL Server;
- изменение моделей или формата JSON без согласования с задачей 2.

## Критерии готовности

- `ContextMiddleware` может получить или создать пользователя через `Catalog.user()`;
- общие клавиатуры и функции отправки используются обеими частями интерфейса;
- формы поддерживают возврат, отмену и очистку состояния;
- `RuleError` показывается пользователю без внутренних деталей исключения;
- главное меню получает список нуля, одного или двух бизнесов;
- третий бизнес нельзя создать через старый callback;
- владелец может менять только свой бизнес;
- поиск возвращает существующий профиль и безопасную ошибку для неизвестного кода;
- избранное добавляется и удаляется без дубликатов;
- настройки проходят через общие проверки;
- результат сохраняется в JSON через Repository;
- методы не импортируют типы Aiogram.

## Проверка результата

1. Создать пользователя через `Catalog.user()`.
2. Передать тестовый update через `ContextMiddleware` и проверить `app` и `actor`.
3. Проверить общую клавиатуру, возврат, отмену и очистку FSM-состояния.
4. Создать два бизнеса и проверить `can_create_business=False`.
5. Проверить отказ при создании третьего бизнеса.
6. Проверить запрет изменения чужого бизнеса.
7. Добавить и удалить бизнес из избранного.
8. Закрыть Repository, открыть его повторно и проверить сохранённые данные.
