# Задача 2. Модели данных и временное JSON-хранилище

## Статус

**В процессе разработки.**

## Цель

Описать данные всей предметной области Notebook и реализовать временное хранилище, чтобы
Telegram-сценарии можно было проверять без установленного SQL Server. Слой хранения должен
поддерживать одинаковые базовые операции для всех моделей и безопасно сохранять JSON.

## Основные файлы задачи

```text
src/notebook_bot/models.py
src/notebook_bot/storage.py
```

`models.py` содержит Pydantic-модели предметной области. `storage.py` содержит
`MemoryTransaction` и `MemoryRepository` с необязательным сохранением JSON.

## Интерфейсная часть задачи

Telegram-интерфейс получает подготовленные модели через сервисный слой. Структура моделей
определяет данные меню, профиля, услуг, клиента, календаря и записей, но обработчики не
должны читать JSON или выполнять SQL-запросы напрямую.

## Логическая часть задачи

Логическая часть включает описание моделей, их связей и независимого контракта временного
хранилища. Сборка приложения подключает реализацию Repository через единый интерфейс.

## Модели, входящие в задачу

| Модель | Назначение | Основные связи |
|---|---|---|
| `User` | Пользователь Telegram | владеет Business, может быть связан с Client |
| `Business` | Независимый профиль и календарь мастера | `owner_id → User` |
| `Service` | Услуга бизнеса | `business_id → Business` |
| `DayRule` | Правило дня недели | `business_id → Business` |
| `DateOverride` | Исключение конкретной даты | `business_id → Business` |
| `TimeNote` | Комментарий и адрес времени | `business_id → Business` |
| `Client` | Клиентская карточка внутри бизнеса | `business_id`, необязательный `user_id` |
| `PersonalDuration` | Длительность услуги клиента | `client_id`, `service_id` |
| `Appointment` | Запись клиента | `business_id`, `client_id`, `service_id` |
| `History` | История действий с записью | `appointment_id`, `actor_id` |
| `Favorite` | Сохранённый специалист | `user_id`, `business_id` |
| `Notification` | Сообщение для фоновой доставки | `user_id`, необязательный `appointment_id` |

## Независимость двух бизнесов

Услуги, расписания, исключения дат, временные комментарии, клиенты и записи содержат
`business_id`. Поэтому два бизнеса одного владельца имеют разные наборы данных. Одинаковая
дата и одинаковое время в двух бизнесах не образуют общий конфликт.

## Снимок записи

`Appointment` хранит `service_name`, `price_rub`, длительность, перерыв и предоплату на
момент создания. Последующее изменение услуги не переписывает историю уже созданной
записи.

Поле `revision` используется для защиты от устаревших карточек и повторных действий.
Статус ограничен утверждённым набором значений.

## Операции транзакции

`MemoryTransaction` реализует:

```text
get(model, id)
list(model, **filters)
put(entity)
delete(model, id)
```

Методы возвращают глубокие копии. Обработчик не должен получить объект из таблицы и
незаметно изменить данные без вызова `put()`.

## Работа `MemoryRepository`

### Режим memory

Если путь не передан, данные существуют до завершения процесса. Режим подходит для
автоматических тестов и короткой ручной проверки.

### Режим JSON

Если передан путь, репозиторий:

1. читает JSON при запуске;
2. проверяет `schema_version`;
3. восстанавливает Pydantic-модели через `TABLES`;
4. создаёт копию таблиц для транзакции;
5. фиксирует копию только после успешного выхода;
6. сериализует значения в JSON-совместимом режиме;
7. записывает результат во временный файл;
8. вызывает `flush` и `fsync`;
9. атомарно заменяет основной файл через `os.replace`.

## Транзакционное поведение

Операции выполняются под `asyncio.Lock`. Если внутри контекста возникает исключение,
изменённый снимок не заменяет рабочие таблицы и не сохраняется в файл. Это даёт rollback
для одного локального процесса.

Реализация не является распределённой блокировкой и не заменяет транзакции настоящей
СУБД. Несколько серверов должны использовать SQL Server-адаптер.

## Повреждённый или неизвестный JSON

При неизвестной версии, отсутствующем обязательном разделе или неверной модели запуск
останавливается с контролируемой ошибкой. Исходный файл не перезаписывается пустыми
данными. Исправление или миграция выполняются отдельно.

## Границы ответственности

В задачу входят:

- модели и их типы;
- внутренние идентификаторы;
- реестр `TABLES`;
- операции временного Repository;
- memory и JSON-режимы;
- атомарное сохранение;
- rollback локальной транзакции.

В задачу не входят:

- SQLAlchemy ORM;
- SQL Server-схема;
- Alembic;
- сетевые транзакции;
- распределённая блокировка;
- бизнес-решение о доступности слота;
- Telegram-кнопки и тексты.

## Требования к будущей совместимости

SQL Server-адаптер должен возвращать те же общие модели и поддерживать контракт операций.
Добавление поля требует одновременной проверки:

- старого JSON;
- новой версии схемы и миграции;
- SQL Server ORM;
- преобразования ORM ↔ Pydantic;
- тестов обоих адаптеров.

Telegram-обработчики не должны менять способ вызова при переключении `STORAGE`.

## Проверка результата

1. Создать пользователя и первый бизнес в JSON.
2. Закрыть Repository и открыть его повторно.
3. Проверить сохранение типов, дат и вложенных интервалов.
4. Создать второй бизнес и убедиться, что выборка по `business_id` разделяет данные.
5. Вызвать исключение внутри транзакции и проверить rollback.
6. Повторить несколько `put()` одного ID и проверить обновление без дубликата.
7. Удалить объект и проверить сохранение удаления.
8. Передать неизвестную версию схемы и проверить отказ без перезаписи файла.
9. Запустить параллельные локальные операции и проверить сериализацию через lock.

## Критерии готовности

- все утверждённые модели описаны и входят в `TABLES`;
- идентификаторы генерируются автоматически;
- фильтры `list()` работают по полям моделей;
- возвращаемые объекты изолированы глубоким копированием;
- успешная транзакция фиксируется;
- исключение выполняет rollback;
- JSON переживает перезапуск процесса;
- сохранение не оставляет частично записанный основной файл;
- повреждённый JSON не уничтожается;
- данные двух бизнесов не смешиваются;
- `.env`, JSON пользователей, lock-файлы и токены исключены из Git.
