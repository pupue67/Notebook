# Будущие модули Notebook

Этот документ описывает назначение заготовок наряду с двумя текущими задачами. Он не является
разрешением реализовывать всё одновременно: каждый модуль получает отдельную постановку,
ветку, критерии готовности и Pull Request.

## `bot/services.py` — Telegram-интерфейс услуг

Нужно реализовать список услуг выбранного бизнеса, создание, изменение и скрытие услуги.
Форма собирает название, цену, режим длительности, минуты фиксированной длительности и
параметры предоплаты. Обработчик проверяет владельца через сервис и не изменяет модели
напрямую.

Готовый экран различает фиксированную и персональную длительность, не показывает клиенту
скрытые услуги и не смешивает услуги двух бизнесов.

## `bot/schedule.py` — рабочая неделя и конкретная дата

Нужно реализовать недельный шаблон с несколькими интервалами, лимитом клиентов и
комментарием каждого дня недели. Разрыв между интервалами моделирует регулярный обед.

Экран конкретной даты должен позволять изменить интервалы только этой даты, закрыть
несколько частей дня, изменить лимит, комментарий и адрес, записать клиента вручную или
сделать день выходным. Отдельная ссылка ведёт к обычному графику соответствующего дня
недели. Существующие записи не удаляются: конфликты показываются для переноса.

## `bot/calendar.py` — единый календарь месяца

Один компонент календаря должен использоваться для горизонта записи, рабочего календаря
мастера, новой записи и переноса. Он отвечает за сетку и навигацию, а доступность получает
из `logic`. Недоступная дата не должна отправлять бизнес-команду.

## `bot/booking.py` — создание записи

Нужно провести клиента по пути «профиль → услуга → дата → время → результат» и поддержать
ручную запись мастером. Для новой персональной услуги создаётся временный резерв, после
чего мастер вводит минуты. Если длительность не помещается, сохраняется исходная
длительность и предлагается выбрать другое время.

## `bot/appointments.py` — карточки и жизненный цикл записей

Модуль показывает списки клиента и мастера, подробную карточку, перенос, отмену,
завершённый визит и неявку. Перенос всегда меняет дату и время. По инициативе мастера новое
время выбирает клиент. Все изменяющие callback используют `revision`.

## `bot/notifications.py` — доставка событий

Telegram-слой получает подготовленные события и выбирает адресата и текст. Нужны
уведомления о создании, ручной записи, переносе, отмене, персональной длительности и
напоминаниях. Подтверждение визита остаётся будущей необязательной настройкой.

## `logic/availability.py` — свободные даты и время

Модуль объединяет недельный шаблон и исключение даты, вычитает закрытые промежутки и
занятые записи, учитывает длительность, перерыв, минимальный срок, горизонт и лимит.
Клиент получает только даты и времена; внутренняя причина недоступности не раскрывается.

## `logic/booking.py` — операции с записью

Сервис создаёт запись, сохраняет снимок услуги, управляет персональной длительностью,
переносом, отменой, предоплатой, историей и напоминаниями. Каждая операция повторно
проверяет права и доступность внутри транзакции.

## `repository.py` — общий контракт хранения

Нужно формализовать протоколы `Repository` и `Transaction`, которыми одинаково пользуются
JSON и SQL Server. Контракт не содержит Telegram-типов и не диктует способ расчёта
доступности.

## `database/models.py` — SQLAlchemy ORM

Требуются таблицы всех сущностей, типы SQL Server, первичные и внешние ключи, ограничения,
индексы и уникальный публичный код бизнеса. Схема изменяется через Alembic, а не вручную
после первого развёртывания.

## `database/repository.py` — SQL Server-адаптер

Адаптер реализует общий Repository, преобразует ORM в Pydantic-модели, выполняет commit и
rollback, не раскрывает строку подключения и предотвращает двойное бронирование при
параллельных запросах.

## `database/db.py` — создание подключения

Фабрика читает `DATABASE_URL`, создаёт async engine и session factory, проверяет
конфигурацию и возвращает Repository. При `STORAGE=json` импорт драйвера SQL Server не
должен мешать локальному запуску.

## Следующие инфраструктурные этапы

После SQL Server потребуются постоянное FSM-хранилище, надёжная очередь уведомлений,
серверное развёртывание, резервные копии, мониторинг и безопасное управление секретами.
Платежи, несколько сотрудников, отзывы, модерация, лист ожидания, абонементы и аналитика
оформляются отдельными продуктовыми задачами после проверки основного сценария записи.
